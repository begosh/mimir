## Native provider preflight and Windows environment inheritance

Windows gives a child process its parent's environment by default. A process that predates a User-scope credential update can therefore lack the key even though a newly launched process would see it. Supplying a child environment block is the documented way to change inheritance for that child; changing registry state or global process state is unnecessary. [Microsoft: Environment Variables](https://learn.microsoft.com/en-us/windows/win32/procthread/environment-variables), [Python subprocess environment](https://docs.python.org/3/library/subprocess.html#subprocess.Popen).

Codex Python SDK 0.163.0 exposes `CodexConfig.env`. Its `client.py` copies `os.environ` and then updates that private copy with `config.env`, before launching its app-server. This supports a narrowly scoped override using the already configured provider key. It does **not** justify copying the complete Windows User/Machine environment into the worker, changing the provider, or exposing key values in diagnostics. [Tagged client source, lines 205-207 and 253-260](https://github.com/openai/codex/blob/rust-v0.163.0/sdk/python/src/openai_codex/client.py), [tagged API reference](https://github.com/openai/codex/blob/rust-v0.163.0/sdk/python/docs/api-reference.md).

The selected custom provider's `env_key` and `env_http_headers` establish names of required variables. Codex also supports other authentication mechanisms, including command-backed auth; absence of `OPENAI_API_KEY` is therefore not sufficient to declare every native Codex session unauthenticated. Configuration comes from multiple layers, and project `.codex/config.toml` files are loaded only for trusted projects. Preflight should inspect the selected provider and report its limited resolution scope, leaving final configuration/authentication to the runtime. [Codex configuration basics](https://developers.openai.com/codex/config-basic), [configuration reference](https://developers.openai.com/codex/config-reference), [authentication](https://developers.openai.com/codex/auth).

Implementation policy: only the selected Codex provider's required variable is read from persisted Windows scopes when entirely absent from Process. Process takes precedence, including an intentionally empty Process variable; User takes precedence over Machine. The resulting dictionary is supplied only to `CodexConfig.env`. Diagnostics contain variable names, boolean presence, chosen scope and local readiness, never values. Static readiness does not mean valid credentials, model access, reachable endpoint or working tools. Non-Codex native login flows are not replaced by this policy.

## Tool selection and permission claims

Codex MCP configuration supports `enabled_tools`, `disabled_tools`, server defaults and per-tool approval modes. The deny list applies after the allow list. Filesystem `read-only` sandboxing alone does not constrain remote MCP side effects; approval policy and tool catalog must also be considered. A prompt requesting read-only research is useful direction but is not an enforcement mechanism. [Codex MCP controls](https://developers.openai.com/codex/mcp), [Codex sandbox/security](https://developers.openai.com/codex/security).

Claude SDK distinguishes available built-ins (`tools`), preapproval (`allowed_tools`), removal (`disallowed_tools`) and PreToolUse hooks. Its callback documentation says `can_use_tool` is invoked only when normal permission evaluation reaches an ask, so it cannot be the sole gate for already preapproved tools. Query policies must specify operations, not approve every tool whose server name sounds like a research source. [Claude SDK tagged types](https://github.com/anthropics/claude-agent-sdk-python/blob/v0.2.172/src/claude_agent_sdk/types.py), [tagged README permission and hook examples](https://github.com/anthropics/claude-agent-sdk-python/blob/v0.2.172/README.md).

Tool descriptions and MCP read-only annotations are evidence about intended behavior; they are not a proof of no side effects. Preserve native denials, explicitly allow known query operations where supported, and disclose remaining catalog limitations. Tool capability probes can check availability and safe operation without attempting writes, but a probe cannot certify arbitrary future tool behavior.

## Usage and cost accounting

The Codex run collector matches usage notifications to the current turn and returns `ThreadTokenUsage`. **Its `last` field is the latest model completion, not necessarily the entire turn:** `TokenUsageInfo.append_last_usage` adds each new usage into `total_token_usage` and replaces `last_token_usage` with that latest usage. A turn that invokes tools can produce multiple model completions. Mímir creates a fresh ephemeral thread for exactly one turn, so the final `usage.total.total_tokens` is the appropriate reported worker total, with `last` optionally retained separately for diagnosis. If threads are reused in future, compute a before/after delta or use genuinely turn-scoped counters; summing cumulative thread totals repeatedly would double-count. Codex's result does not establish a dollar cost, and context-window adjustment/estimation paths can update usage, so describe it as runtime-reported usage rather than authoritative billing. [Tagged run collector](https://github.com/openai/codex/blob/rust-v0.163.0/sdk/python/src/openai_codex/_run.py), [tagged `TokenUsageInfo`, lines 2397-2451](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/protocol/src/protocol.rs#L2397-L2451), [tagged generated usage schema](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/app-server-protocol/schema/typescript/v2/ThreadTokenUsage.ts).

Claude SDK 0.2.172 `ResultMessage` exposes `total_cost_usd`, `usage` and `model_usage`; the model-usage mapping preserves native camelCase fields. These can be retained with an explicit provenance label. Missing usage is unknown, not zero, and cached input must not be added again if already included by the provider's total. [Tagged result types](https://github.com/anthropics/claude-agent-sdk-python/blob/v0.2.172/src/claude_agent_sdk/types.py#L1670-L1710).

OpenCode 1.19.3's `AssistantMessage` contains `cost` and `tokens` fields: input, output, reasoning, cache.read/cache.write and optional total. The server's native values can be reported with their source; do not silently invent a total by adding potentially overlapping counters. [Tagged OpenAPI `AssistantMessage`](https://github.com/anomalyco/opencode/blob/v1.19.3/packages/sdk/openapi.json).

An engine metric should distinguish model calls, measured elapsed time, parallel wall time, reported tokens, measured costs and unknown fields. A single-worker comparison must use the same objective/evidence/tool permissions/model and input budget; fewer calls alone does not establish preserved answer quality.

## Durable execution and recovery

MCP stdio requires stdout to contain valid protocol messages only. Human progress belongs in tool results, journal artifacts or stderr; mixed prints corrupt host transport. MCP connection lifetime and a Mímir durable run are separate contracts. [MCP 2025-11-25 transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

Atomic `os.replace` provides atomic publication for an individual file when successful; it does not make several files and a journal one transaction. Ownership locks release when their process exits, but release is not proof that cleanup completed. A checkpoint should distinguish worker execution, publication identities, cleanup and successful phase completion. [Python `os.replace`](https://docs.python.org/3/library/os.html#os.replace), [Python `fcntl.flock`](https://docs.python.org/3/library/fcntl.html#fcntl.flock), [Windows file locking](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/locking?view=msvc-170).

Accordingly, publication recovery should first validate owned report/sidecar identities from the checkpoint, then retry the failed lifecycle step. It must not repeat inference or learning append merely because metadata lagged a successfully published file. Partial worker responses cannot be reclassified as successful output. Cleanup failure should remain visible while already written artifacts remain accessible with an incomplete-state qualification.

## Learning state, provenance and installation identity

Python's `Path(__file__)` identifies executable source location, while `Path.cwd()` identifies the current workspace. Using package-relative writable learning storage causes installed skill and repository execution to diverge. A configured project state path should own curated guidance and a separate append-only candidate stream; an installed skill should supply instructions rather than receive project-specific writes. [Python `pathlib`](https://docs.python.org/3/library/pathlib.html#pathlib.Path.cwd).

Learning policy here is a design decision: `off` reads/writes nothing; `read` is the default and reads curated guidance or workspace legacy standing guidance without modifying it; `write` records unvalidated candidates only. Default legacy fallback excludes historical dated generated run records and labels its standing guidance unvalidated; explicitly configured guidance paths preserve the caller's selected note content. Candidate records do not automatically become prompts or standing instructions. Use a stable source/report identity for append idempotency, retain a reference to the report, and leave promotion to explicit review. No silent migration, overwrite or deletion is needed.

Runtime SHA-256 identifies the bytes inspected, and a Git revision identifies a repository commit. Neither establishes factual claim verification, dirty-worktree absence, installed dependency compatibility or authenticated harness readiness. An inference-free diagnostics report should expose both code identities, interpreter, actual package versions, workspace, run root, guidance/candidate paths, and credential presence separately. [Python `hashlib`](https://docs.python.org/3/library/hashlib.html), [Python `importlib.metadata`](https://docs.python.org/3/library/importlib.metadata.html).

## Remaining qualifications

- Static native configuration inspection is deliberately narrower than Codex's complete managed policy/profile resolution; the runtime remains authoritative.
- Installed SDK/source contracts establish API shape, not that all four local harnesses authenticate successfully. Claude's prior HTTP 401 and OpenCode's prior native configuration timeout remain unresolved until live probes pass.
- Runtime pooling, pruning, reflection and context compression require comparative quality/latency evaluation. Their benefit is not established by API documentation or deterministic lifecycle tests.
- Source records, citations and content hashes establish provenance and identity. Independent source-to-claim checks and retrieval completeness remain explicit evidence properties.
